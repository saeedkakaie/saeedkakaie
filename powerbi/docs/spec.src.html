۰. این بسته چیست و از کجا شروع کنیم

برنامه IBP شش شرکت هلدینگ را در یک چرخه ماهانه برنامه‌ریزی می‌کند: پورتفوی ← پیش‌بینی آماری ← برنامه تقاضا و اجماع ← برنامه تولید و ظرفیت ← موجودی و مواد ← مالی و سناریو ← جلسه مدیریت. این سند همان منطق را برای Power BI بازنویسی می‌کند. هر فرمول این‌جا عیناً همان کد برنامه است و برای هر عدد مهم، مقدار مرجع برنامه آمده تا خروجی Power BI با آن مقایسه شود.

۴. قراردادهای عمومی

چرخه و پنجره‌های زمانی

هر شرکت ماه چرخه خودش را دارد: c = Company[CycleIndex]. ماه c اولین ماه برنامه است و آخرین ماه دارای فروش واقعی c−1 است.

پنجرهMonthIndex
۱۲ ماه اخیر (LTM)c−12 … c−1
۱۲ ماه قبل از آنc−24 … c−13
۳ ماه اخیرc−3 … c−1 (و همان ماه‌های سال قبل: c−15 … c−13)
۱۲ ماه آیندهc … c+11
۶ ماه آینده (هشدار ظرفیت، ریسک تقاضا)c … c+5

چون شرکت‌ها ممکن است چرخه متفاوت داشته باشند، اندازه‌های پنجره‌دار با الگوی زیر روی شرکت‌ها جمع زده می‌شوند (در نمای هلدینگ هم درست است):

SUMX ( VALUES ( Company[CompanyCode] ),
    VAR c = CALCULATE ( MAX ( Company[CycleIndex] ) )
    RETURN CALCULATE ( [Revenue], REMOVEFILTERS ( 'Period' ), 'Period'[MonthIndex] >= c - 12, 'Period'[MonthIndex] <= c - 1 ) )

واحدها

Tons = qty × unitWeightKg / 1000 PriceList(t) = unitPrice × (1 + priceInflation)^(MonthIndex(t) − c) AvgDiscount = Σ_channel ( customers_in_channel × discount ) / Σ customers (وزن = تعداد مشتری هر کانال) Value(t) = qty × PriceList(t) × (1 − AvgDiscount) (مبلغ برآوردی پیش‌بینی، ستون Forecast[RevenueEst])

بهای تمام‌شده فروش واقعی گذشته (ستون Sales[CostDeflated]) با همان تورم قیمت به گذشته برده می‌شود: qty × unitCost × (1+priceInflation)^(MonthIndex − c) و سود ناخالص واقعی = درآمد − آن.

۵. مرحله ۱ — پورتفوی محصول DAX ستون

ستون‌های محاسباتی روی جدول Product (بخش ۰۹ فایل DAX). همه روی ۱۲ ماه اخیر شرکت همان محصول.

Revenue12 = Σ revenue (c−12 … c−1) Cost12 = Σ CostDeflated Qty12, QtyPrev12 = Σ qty در ۱۲ ماه اخیر و ۱۲ ماه قبل از آن Margin12 = 1 − Cost12 / Revenue12 VolumeGrowth = Qty12 / QtyPrev12 − 1 (اگر QtyPrev12 > 0)

ABC (پارتو درآمد)

CumShareBefore = Σ Revenue12 محصولات پرفروش‌ترِ همان شرکت (بدون خود محصول) / Σ Revenue12 شرکت Class = C اگر Revenue12 ≤ 0 ؛ A اگر CumShareBefore < abcA ؛ B اگر CumShareBefore < abcB ؛ وگرنه C

نکته: معیار «سهم تجمعی قبل از محصول» است (نه بعد از آن)؛ بنابراین محصولی که از مرز ۸۰٪ عبور می‌کند هنوز A است.

XYZ (نوسان)

q_m = فروش هر ۱۲ ماه (ماه بدون فروش = 0) CV12 = σ_pop(q) / mean(q) (انحراف معیار جامعه، تقسیم بر 12) X اگر CV12 ≤ xyzX ؛ Y اگر CV12 ≤ xyzY ؛ وگرنه Z (و Z اگر فروشی نبوده)

الگوی تقاضا (Syntetos–Boylan)

n = تعداد ماه‌های دارای فروش از 12 ؛ ADI = 12 / n CV² = (σ_pop / mean)² فقط روی ماه‌های دارای فروش ADI < 1.32 و CV² < 0.49 → هموار ؛ ADI < 1.32 و CV² ≥ 0.49 → نامنظم ADI ≥ 1.32 و CV² < 0.49 → متناوب ؛ ADI ≥ 1.32 و CV² ≥ 0.49 → کلوخه‌ای

۸. دقت پیش‌بینی، FVA و سیگنال ردیابی PQ DAX

ساخت جدول Accuracy (Power Query)

دانه: شرکت × محصول × ماه × نسخه. مقایسه همیشه با پیش‌بینی lag-1 است: پیش‌بینی‌ای که در چرخه ماه قبل برای این ماه ثبت شده.

  • برای اجماعی و آماری: فقط ماه‌هایی که آن نسخه پیش‌بینی lag-1 دارد. در آن ماه‌ها، اجتماع «محصولات دارای فروش» و «محصولات دارای پیش‌بینی» گرفته می‌شود؛ پیش‌بینی یا فروش نبوده = 0.
  • ساده: پیش‌بینی = فروش ماه قبل همان محصول (اگر نبوده 0).

اندازه‌ها

WMAPE = Σ|F − A| / ΣA Accuracy = max(0, 1 − WMAPE) (فقط اگر ΣA > 0) Bias = Σ(F − A) / ΣA (+ بیش‌برآورد ، − کم‌برآورد) FVA آماری = Accuracy(آماری) − Accuracy(ساده) FVA قضاوت = Accuracy(اجماعی) − Accuracy(آماری) (مثبت = جلسه اجماع ارزش افزوده) Accuracy 3M / Bias 3M = همان با نسخه اجماعی در c−3 … c−1 (مرجع داشبورد و کارنامه) Tracking Signal (هر محصول) = Σ(F − A) / mean|F − A| ؛ |TS| > 4 = سوگیری مداوم
دقت در سطح هر تجمیع با WMAPE همان تجمیع محاسبه می‌شود (نه میانگین دقت محصولات). مقدار مرجع: ZMC دقت ۳ ماه ۷۶٫۷٪ و سوگیری ۶٫۰٪+.

۱۷. امنیت (RLS) و بروزرسانی خودکار

RLS

جدول UserAccess(UserEmail, CompanyCode)؛ * یعنی همه شرکت‌ها. نقش «Company Access» با این فیلتر روی Company و همان الگو (با ستون CompanyCode خودشان) روی Customer، Channel، Region، Family و Supplier که به Company رابطه ندارند:

VAR u = USERPRINCIPALNAME ()
RETURN
    CONTAINS ( FILTER ( UserAccess, UserAccess[UserEmail] = u ), UserAccess[CompanyCode], Company[CompanyCode] )
 || CONTAINS ( FILTER ( UserAccess, UserAccess[UserEmail] = u ), UserAccess[CompanyCode], "*" )

دسترسی‌ها می‌توانند از کاربران سرور مرکزی برنامه (نقش و شرکت‌های مجاز) استخراج شوند تا یک منبع حقیقت باشد.

بروزرسانی

  1. Task Scheduler ویندوز (یا cron) روی سرور: export_data.py سپس ibp_pbi.py (مثلاً هر شب ۲:۰۰ و دستی بعد از جلسه اجماع).
  2. Power BI Service: On-premises data gateway روی همان سرور با دسترسی به پوشه‌ها؛ Scheduled refresh بعد از پایان اسکریپت (مثلاً ۳:۰۰).
  3. اسکریپت پایتون را داخل Power Query اجرا نکنید (در Service فقط با Personal gateway کار می‌کند و کند است)؛ اجرای جداگانه پایدارتر است.
  4. برای داده زیاد: به‌جای CSV در SQL Server بنویسید (DataFrame.to_sql) و Power Query را به SQL وصل کنید.

۲۰. نکات، تفاوت‌ها و محدودیت‌ها

  • فایل‌های DAX و M با منطق برنامه نوشته و منطق آن‌ها با معادل پایتون آزموده شده، اما در خود Power BI Desktop اجرا نشده‌اند؛ ممکن است نام ستون یا نوع داده نیاز به اصلاح جزئی داشته باشد. معیار درستی، اعداد بخش ۱۸ است.
  • تعریف «دقت ۳ ماه» در داشبورد و کارنامه: نسخه اجماعی، lag-1، WMAPE تجمیعی سه ماه. صفحه تقاضای برنامه دقت را برای هر ماه جداگانه هم نشان می‌دهد؛ هر دو در DAX ممکن است (با فیلتر Period).
  • RCCP (بخش ۹-۴) بدون محدودیت است و با بار برنامه محدود (ResourceLoad) فرق دارد؛ هشدار ظرفیت برنامه از RCCP استفاده می‌کند.
  • اگر برای یک محصول دو مسیر priority 1 با نرخ برابر وجود داشته باشد، برنامه اولی را برمی‌دارد ولی ستون IsPrimaryRCCP هر دو را علامت می‌زند؛ چنین داده‌ای را اصلاح کنید.
  • هزینه نگهداری و موجودی پایانی بر اساس بهای واحد ثبت‌شده محصول (unitCost) است، نه بهای استاندارد.
  • پیش‌بینی آماری پایتون (موتور کامل) ممکن است با نسخه آماری ذخیره‌شده در برنامه (اگر بدون موتور اجرا شده باشد) فرق کند.
  • برای هر شرکت جدید فقط داده و تنظیماتش لازم است؛ مدل و اندازه‌ها چندشرکتی هستند.
